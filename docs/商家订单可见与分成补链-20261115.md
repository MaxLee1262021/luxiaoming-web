## 问题与修复

此前商家端仅查询正式分成流水，未到入账时点的关联订单完全不可见。同时，分成只读取扫码绑定历史，没有使用服务端已经核验并冻结的订单商家来源；扫码上报遗漏时，订单即使显示商家，也可能被判成无商家。

本次补齐两条链路：

- 商家端新增关联订单，按下单月份展示脱敏单号、日期、整单实收及分成进度：待付尾款、退款观察期、待入账、已入账、需核查。关联订单与正式分成流水各自分页；流水仍按实际入账月份统计，未入账金额不会加入已入账净额。
- 自主订单 T1 可使用持久订单的商家码来源补齐分成证据。服务端重新核对商家、二维码、原始预约时间和历史码有效期，不使用客户端临时商家字段或用户最近扫码猜测归属。后续扫码不会夺走已冻结订单。证据保存于分成任务，刷新、重启及窗口结束重算时保留。

订单来源核验时间保存在 `source.validatedAt`；旧预约没有该字段时回读原私有预约创建时间。码在下单后被替换，不会使有效的原始来源消失。闭店重开及用户注销仍能使旧证据失效，新来源证据按发生时间重新判断。客服订单 T2 保留既有历史窗口规则。

正式分成仍要求已确认的线上尾款或零尾款完成凭证，并经过商家配置的退款观察期。成功退款按现有规则减少基数或追加冲抵，不更新已有正式快照。引擎版本升为 `1.2.0`，无需数据库结构迁移。

## 单笔历史修复工具

`scripts/recover-merchant-order-source.cjs` 默认只读，禁止自动迁移，不建立绑定、不启用分成、不直接写入资金流水。示例：

```powershell
node scripts/recover-merchant-order-source.cjs --root "D:\idea\travel-photo\luxiaoming-admin-交付包" --order-no LS2026111564E191677A --merchant-id sm_10ed12fdd07dee509cda436c
```

输出包含脱敏单号、商家、匹配扫码、原预约时间、实收、比例、观察期、预计分成、入账时间及启用状态。无扫码、多个商家歧义、冲突来源、已存在任务或快照均拒绝自动补正。T2 历史订单要求按完整历史矩阵单独复核。

只有明确执行 `--apply`，并提供 `--reason`、`--operator-id`、`--request-key`，才会通过并发比较更新指定订单来源，原子追加订单修复记录，并写入分成审计。已线上付清尾款的订单同时置 `shareEnqueuePending`，交给既有任务接收。不会改动另一笔订单。重复执行同一已修复来源不重复追加修复记录。

真实修复前应停止该应用的分成任务调度或使用维护窗口，避免独立 worker 与来源补正并发创建任务。工具发现资金任务竞态会明确返回需复核，保留已有资金记录。
