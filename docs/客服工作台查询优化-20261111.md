# 客服工作台查询优化

工作台打开时原先请求汇总、待办、预占三次，每次业务读取都会加载二十多张表；权限检查还会两次逐个查询菜单属性。预占列表每秒请求，加重了远程 MySQL 往返开销。

本次修改如下：

- 新增 `GET /api/kf/workbench/overview?mode=workbench|intake&tab=pool|mine`，同一只读事务返回概览、当前分页和预占条。旧接口继续可用。
- `svcStore.read` 接收查询上下文，按接口读取必要表、当前权限范围内订单及其关联数据。写入事务继续使用原完整快照和校验，查询不执行支付回放或建绑。
- GET 内使用本次请求的关联索引，分页后再组装明细展示。权限和业务状态不做跨请求缓存。
- 菜单属性改为一次批量读取，权限计算与会话展示复用同一次菜单读取；停用账号或撤销授权仍在下一请求生效。
- 工作台首屏三次请求合并为一次，订单承接两次合并为一次。预占同步间隔改为五秒，倒计时本地每秒刷新。切换筛选或离开页面取消旧请求，后台请求不重叠。
- 原有共享订单表和支付事件表存在不同排序规则，关联比较使用二进制订单标识，避免跨表排序规则冲突。

不需要额外 SQL 迁移。本次未修改真实业务数据。

## 实测

同一台机器、同一个已配置远程 MySQL，以真实权限存储和 API 处理器进行只读采样。临时认证会话仅在本地内存，不新建账号、不写业务数据。结果不含凭据或客户内容。

| 测量项 | 优化前 | 优化后 |
|---|---:|---:|
| 汇总业务读取 | 830 ms / 25 次 SQL | 258 ms / 4 次 SQL |
| 含权限校验的汇总接口 | 3711 ms / 126 次 SQL | 536 ms / 11 次 SQL |
| 工作台首屏请求组 | 8547 ms / 378 次 SQL / 3 次 HTTP | 368 ms / 11 次 SQL / 1 次 HTTP |

SQL 次数包含采样所需的只读事务声明。网络往返存在波动，上表为单轮测量；当前数据库中的工作台订单为空，数字主要反映网络和查询数量的改进，不代表大规模订单压测。现阶段订单仍在权限限定范围内读取后按业务条件分页；超大数据量需要继续把聚合和分页下推 SQL。

原始记录：工作区 `outputs/svc-query-performance/before.json`、`after.json`。浏览器记录：`outputs/svc-workbench-performance/browser.json`。

## 验证

自动测试比较按需读取和原完整快照在超级管理员、客服、直属主管及财务下的结果，覆盖汇总、待办、承接、预占、详情、客诉、保护绑定及链接查询。另验证合并接口与旧接口结果一致、分页/过滤独立、撤销菜单即时生效、旧响应不覆盖新筛选、只读查询无写入，以及原客服和摄影师账务事务不受影响。

真实 Chrome 使用隔离测试数据验证：首屏一次查询、倒计时一秒内变化但不请求、五秒后才同步预占、承接两标签筛选正确，页面脚本错误为零。完整回归结果见 `outputs/svc-query-performance/tests.log`。

最终完整测试 988 项：978 通过、10 跳过、0 失败。语法检查覆盖 158 个模块，构建检查通过。本地 `http://127.0.0.1:5192/` 已重启，健康接口返回正常，MySQL、Redis 可用；新前端脚本已提供合并查询，未登录访问仍返回 401。
