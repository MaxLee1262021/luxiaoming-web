# 现场拍摄与支付流程（2026-11-16）

本版本依据最新业务确认：游客浏览免登录，提交预约前微信登录；至少选择一项摄影服务，影像周边只能加购。联系人电话可授权或手填，期望日期和时段必填但不锁档。预约须知由服务端下发版本，建单保存用户同意事实。

主状态统一为 **已预约 → 已定档 → 拍摄中 → 已完成**，取消“待支付定金”订单状态。状态编码继续使用 `reserved / awaiting_shoot / shooting / completed`，兼容旧名称；“待付尾款”和“待确认完成”作为辅助提示，不覆盖四态主标签。实物订单维持独立的待付款、待发货、待收货和已完成流程。

提交预约时先保存独立预约支付信息，按服务端商品快照计算定金并在预约表单调起支付。只有微信验签回调或验签查单确认到账后才创建正式预约单，初始状态为“已预约”，无财务审核。支付取消、失败或确认中均停留在预约表单，不进入预约成功页，不出现在我的订单和后台履约列表中。重复提交、查单及重复回调复用同一预约支付信息，到账后最多生成一笔正式订单。

小程序支付成功回调只触发后端查单，不能作为建单或成功跳转依据。回调延迟时保留预约支付标识和表单，用户可查询确认结果；已经到账的请求不会再次收费。后台不再提供先建未付款订单的入口。零定金商品沿用服务端免定金配置，不创建零元微信支付。

客服领取已预约订单后沟通实际时间、地点和摄影师；只有实际安排摄影师后才进入“已定档”，填写预约日期或空派单记录不会推进状态。摄影师保留人员资料供派单，不登录后台。客服工作台继续保留认领、确认时间、派单、尾款等内部子状态，不将“复购预占”等内部状态直接映射为已预约。

游客在本人已定档订单的详情页点击“到达点位”，弹窗二次确认：“请确认您已到达约定的拍摄地点，确认后订单将进入‘拍摄中’。”按钮为“暂未到达”和“确认到达”。取消不提交；确认后调用 `confirmOrderArrival`，以服务端返回为准进入拍摄中。到达仅为用户自行声明，不采集定位或核验扫码；服务端校验有效派单、定金条件、本人身份及订单未取消、未冻结或被售后锁定。提交期间防重复点击，重复请求只记录一次，失败可重试。

到达时间 `customerArrivedAt` 与实际开拍时间 `shootingStartedAt` 分别记录，客服工作台同步进入拍摄中并展示到达记录。确认到达后立即开放“支付尾款”入口，到达本身不代表拍摄已结束。客服安排摄影师触发“已定档”，其余主状态由客户动作和支付结果自动更新，不需要客服登记开始拍摄或拍摄完成。

游客到达后可直接点击“支付尾款”，点击即确认本次拍摄并同意支付尾款。不存在客服登记拍摄完成或后台选片审批门禁。发起支付、取消支付、支付失败或仍在处理中时保持“拍摄中”，只有尾款经服务端确认到账后才进入“已完成”，并同步客服工作台。交付记录和附加服务跟进独立保存。零尾款订单在到达后开放“确认完成订单”，客户确认后结清，不创建零元微信支付单。

已收定金冻结；尾款支付发起前客服可记录换商品、加购、赠送和优惠，保存原因和变更历史。尾款支付单尚有效时金额锁定；总价低于已收定金的调整走退款异常处理。尾款到账后商品和金额不再修改，后续周边/承诺事项由客服创建跟进单。

未支付成功时关闭支付窗口即可返回表单，正式订单尚未创建。若需要修改联系人或拍摄项目，点击修改预约信息，由服务端查单并安全关闭原支付后解锁表单；已到账则恢复正式预约结果，查询或关单失败时保留原预约信息。“已预约”且尚未安排过摄影师的已付款订单，在列表和详情显示“申请退款”。游客确认申请后，系统取消预约并自动按原支付交易退还已支付且未退款的金额，无需客服或财务审核，不进入售后订单、售后记录及财务待审。退款使用稳定请求号，重复提交或查询不会重复退款；渠道处理中、异常及成功分别展示，只有微信确认成功才记为已退款。退款账本保留在现有存储中，按用户自动退款来源与业务售后工单隔离。

客服主动提交的售后服务单使用独立流程：提交售后问题 → 售后联系客人并保存联系记录 → 售后确认退款金额并提交 → 财务审核通过 → 微信原路退款。新建售后问题不会直接进入财务审核；服务端拒绝跳过联系记录、直接审核和通过普通编辑修改退款状态。财务驳回后返回售后处理，已执行退款使用原退款单查询渠道结果。历史已存在的安排前定金退款审核单保留兼容处理，新提交的用户预约退款统一自动处理。线上收款均不经过财务审核；线下收款核对独立处理。

每个门店只生成一个固定小程序码，所有位置使用同一码。生成成功后旧位置码停用并保留历史。扫码事件按上海自然日统计，微信用户按日去重，匿名访客只计次数。来源采用当前小程序会话内最近一次有效扫码，订单创建后冻结。

## 迁移和回退

新字段继续使用现有 MySQL typed leaf/关系表存储，不扩大已接近行大小限制的订单主表。JSON 与 MySQL 使用相同业务投影。

预约支付草稿独立存放在 `bookingRequests`，不通过后台通用集合写接口开放。MySQL 发布前运行正式 schema 迁移，以建立草稿主表与支付索引表。旧版本遗留的未收定金订单不再出现在正常订单列表及经营统计中，保留原记录供支付回调补偿和人工核对，不伪造已预约或已收款事实。

本次状态更名保留原编码，历史订单通过展示投影使用新名称，不批量改写历史流转事实或补造到达记录。新增到达字段沿用现有 typed leaf 存储。小程序和后台须配套发布，验证用户确认到达后前后台状态一致，以及重复到达、售后冻结和尾款支付门禁。

运行迁移默认只读，输出需变化的订单数和人工核对清单：

```powershell
node scripts/migrate-order-flow.cjs --json=server/data/db.json
node scripts/migrate-order-flow.cjs --mysql
```

维护窗口内追加 `--apply` 写入；工具先备份完整订单到本地 `.codex-tmp/order-flow-backups`，然后逐笔检查快照并迁移。发生并发变化的订单保留现场并列入 conflicts，可重跑。已取消订单不恢复；已确认尾款的旧订单映射完成；缺尾款事实的旧完成/交付订单标为待核对，不补造收款。

回退使用同一数据源和工具返回的备份路径，维护窗口内执行：

```powershell
node scripts/migrate-order-flow.cjs --json=server/data/db.json --restore=备份路径 --apply
node scripts/migrate-order-flow.cjs --mysql --restore=备份路径 --apply
```

本次代码修改不自动连接生产数据库、执行真实迁移、发起支付或生成外部小程序码。发布时小程序、后台和数据迁移必须作为同一组版本验证。
