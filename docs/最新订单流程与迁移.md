# 现场拍摄与支付流程（2026-10-16）

本版本依据最新业务确认：游客浏览免登录，提交预约前微信登录；至少选择一项摄影服务，影像周边只能加购。联系人电话可授权或手填，期望日期和时段必填但不锁档。预约须知由服务端下发版本，建单保存用户同意事实。

主状态统一为 **待确认 → 待拍摄 → 拍摄中 → 已完成**，取消“待支付定金”订单状态。

提交预约时先保存独立预约支付信息，按服务端商品快照计算定金并在预约表单调起支付。只有微信验签回调或验签查单确认到账后才创建正式预约单，初始状态为“待确认”，无财务审核。支付取消、失败或确认中均停留在预约表单，不进入预约成功页，不出现在我的订单和后台履约列表中。重复提交、查单及重复回调复用同一预约支付信息，到账后最多生成一笔正式订单。

小程序支付成功回调只触发后端查单，不能作为建单或成功跳转依据。回调延迟时保留预约支付标识和表单，用户可查询确认结果；已经到账的请求不会再次收费。后台不再提供先建未付款订单的入口。零定金商品沿用服务端免定金配置，不创建零元微信支付。

客服领取待确认订单后沟通实际时间、地点和摄影师；只有实际安排摄影师后才进入“待拍摄”，填写预约日期或空派单记录不会推进状态。客服确认到场后手动登记“开始拍摄”，进入“拍摄中”。摄影师保留人员资料供派单，不登录后台。

客服在现场拍摄结束后登记“拍摄完成”，游客才可查看成片并点击“支付尾款”，代表认可现场照片。不存在后台选片审批门禁。登记拍摄完成、记录选片和交付均不提前结束主订单；尾款仍在处理中时保持“拍摄中”，只有尾款经服务端确认到账后才进入“已完成”。交付记录和附加服务跟进独立保存。零尾款订单通过确认现场拍摄完成结清，不创建零元微信支付单。

已收定金冻结；尾款支付发起前客服可记录换商品、加购、赠送和优惠，保存原因和变更历史。尾款支付单尚有效时金额锁定；总价低于已收定金的调整走退款异常处理。尾款到账后商品和金额不再修改，后续周边/承诺事项由客服创建跟进单。

未支付成功时关闭支付窗口即可返回表单，正式订单尚未创建。若需要修改联系人或拍摄项目，点击修改预约信息，由服务端查单并安全关闭原支付后解锁表单；已到账则恢复正式预约结果，查询或关单失败时保留原预约信息。已付定金且尚未安排过摄影师的订单可以退定金：游客在小程序点击“申请退定金”，提交后生成待处理售后工单，由客服处理、财务审核并记录实际退款；派单或拍摄后仍进入异常/售后审核。退款保留金额、原因和外部流水，系统不把人工审核记录冒充微信退款执行。线上收款均不经过财务审核；线下收款核对和退款审核独立处理。

每个门店只生成一个固定小程序码，所有位置使用同一码。生成成功后旧位置码停用并保留历史。扫码事件按上海自然日统计，微信用户按日去重，匿名访客只计次数。来源采用当前小程序会话内最近一次有效扫码，订单创建后冻结。

## 迁移和回退

新字段继续使用现有 MySQL typed leaf/关系表存储，不扩大已接近行大小限制的订单主表。JSON 与 MySQL 使用相同业务投影。

预约支付草稿独立存放在 `bookingRequests`，不通过后台通用集合写接口开放。MySQL 发布前运行正式 schema 迁移，以建立草稿主表与支付索引表。旧版本遗留的未收定金订单不再出现在正常订单列表及经营统计中，保留原记录供支付回调补偿和人工核对，不伪造待确认或已收款事实。

运行迁移默认只读，输出需变化的订单数和人工核对清单：

```powershell
node scripts/migrate-order-flow.cjs --json=server/data/db.json
node scripts/migrate-order-flow.cjs --mysql
```

维护窗口内追加 `--apply` 写入；工具先备份完整订单到本地 `.codex-tmp/order-flow-backups`，然后逐笔检查快照并迁移。发生并发变化的订单保留现场并列入 conflicts，可重跑。已取消订单不恢复；已确认尾款的旧订单映射完成；缺尾款事实的旧完成/交付订单标为待核对，不补造收款。

回退使用同一数据源和工具返回的备份路径，维护窗口内执行：

```powershell
node scripts/migrate-order-flow.cjs --json=server/data/db.json --restore=备份路径 --apply
node scripts/migrate-order-flow.cjs --mysql --restore=备份路径 --apply
```

本次代码修改不自动连接生产数据库、执行真实迁移、发起支付或生成外部小程序码。发布时小程序、后台和数据迁移必须作为同一组版本验证。
