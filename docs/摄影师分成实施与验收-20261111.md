# 摄影师分成实施与验收

依据：用户提供的《摄影师分成管理开发需求说明 DEV-SHR-003（定稿）》与《摄影师分成模块交互演示 DEMO-PH v1.4》，以及回传《摄影师分成-待确认事项与验收记录-20261111(1).xlsx》的七项结论。用户已明确要求按结论继续开发；结论覆盖原待决事项。本次未执行生产发布、真实业务库迁移、删除或真实消息发送。

## 功能与存储

已接入 PH-01 比例设置、PH-02 分成明细、PH-03 结算管理、PH-04 摄影师列表、PH-05 新增摄影师和 PH-06 我的分成。前端路由键依次为 `photoRules`、`photoLedger`、`photoSettlement`、`photoParty`、`photoNew`、`photoMine`。

本模块只新增三张业务表：`photo_profile`、`photo_settlement`、`photo_profile_log`。规则和明细复用 `benefit_rule`、`benefit_ledger`，按 `beneficiary_type='photo'` 隔离；派单与调账复用 `svc_assign_log`、`svc_adjust`，通知复用 `svc_notification`。`photo_profile` 的写入白名单不含在途数量；列表与终止接口每次查询订单实时计数。`019_photo_share.sql` 增加订单 `(photo_id,service_status)` 索引、手机号唯一约束和每人每月结算单唯一约束。

金额使用分整数，按 `floor(net_amount_fen × rate_bp / 10000)` 计算。四类独立，个人规则优先，支付时点取版本；客服与摄影师共用 `svcBenefit.rateBpOf`。规则版本在共用事务锁下全局分配，保存后次日北京时间零点生效。摄影师没有观察期，`wait_days` 仅展示，按完成月入草稿。

转派保留原人明细；未进结算单直接置零、草稿剔除重算、已推送/已认可保留历史快照并产生下期 `void` 调账、已发放产生最多三期冲抵计划。冲抵不使实发变负，超过三期的余额保留记录并告警。重复通知、转派和置零事件有幂等处理。

## 接口与身份

接口以 `/api/photo` 为前缀，使用 `{code,msg,data}` 响应；4301～4308 按定稿业务错误约定返回。

| 资源 | 接口 |
|---|---|
| 规则 | `GET/POST /rule`、`POST /rule/preview` |
| 明细 | `GET /ledger`、`GET /ledger/export`、`POST /ledger/batch-settle` |
| 档案 | `GET/POST /party`、`POST /party/{id}/rate`、`POST /party/{id}/status` |
| 结算 | `GET/POST /settlement`、`POST /settlement/{id}/push`、`POST /settlement/{id}/accept`、`POST /settlement/{id}/pay` |
| 本人 | `GET /me`；本人导出使用 `/ledger/export`，由会话强制限定本人 |

管理员保存新增摄影师时自动分配 `PHYYYY0001`，同时使用管理员填写的登录账号和登录密码创建系统账号，并绑定 `subject_type='photo'` / `subject_id=PH编号`。账号输入方式按 2026-11-13 的最新要求参照新增商家，PH 编号与登录账号分开。档案、初始比例、留痕及认证账号在同一事务中提交，任一写入失败整体回滚；现有账号或已停用角色不被覆盖或自动启用。服务端与界面均限制只有管理员能建档。

密码使用既有哈希格式保存，不在建档响应中返回。保存成功、取消、离开页面或切换账号后清除表单密码，不写入浏览器存储、分成日志、查询或导出。摄影师使用管理员填写的凭据登录后可自行改密；忘记时使用权限中心重设，不生成第二个旧人员身份。操作说明见[摄影师账号同步创建](摄影师账号同步创建-20261113.md)。

存量摄影师账号不迁移、不重绑。未绑定 PH 编号的旧摄影账号继续返回 `PHOTOGRAPHER_LOGIN_DISABLED`。PH-06 不按请求中的摄影师参数切换身份，外部摄影师仅有本人只读和导出权限，不能进入订单接单/拒单页面或管理其他摄影师。

后台账号仍按服务端菜单和角色校验。前端隐藏按钮之外，服务端再次限制管理接口、本人明细和本人 CSV。后台导出为十列，本人导出为九列，含 UTF-8 BOM、完整 OpenID，并防止 CSV 单元格公式注入。

## 订单集成与兼容

客服工作台派单/转派先写 `orders.photo_id` 和 `svc_assign_log`，再在同一连接、同一事务提交前调用摄影师会计逻辑；摄影师计酬无需接单确认。客服分成不再使用自己的观察期、判责和结算算法修改摄影师明细。

旧订单动作通过 `photoOrderBridge` 转换事实，并在订单事务内补齐共享派单/转派记录。旧字段 `photographerId` 与新字段 `photo_id` 不一致时，使用本次实际变更的字段；订单完成不受迁移默认 `service_status='new'` 阻挡。实际支付时间优先于创建时间，不以创建时间捏造支付事实。没有支付时间或未派单的订单不生成明细。

旧派单记录的沟通渠道能够识别时存 `wechat` / `phone` / `face`；未提供时明确记为 `legacy`，不伪造电话确认。新客服工作台仍要求实际沟通渠道。存量身份不自动猜测映射，不再执行历史分成回填。

摄影师金额以独立分成账本为准。原月度对账不再按保留的旧订单计算摄影师应付额或推断总部收入，提供独立账本入口。旧摄影师对账、发放与冲正接口返回 409，避免在清理后重建旧应付金额；分销等其他财务流程保留。

共用表的北京时间 `DATETIME` 在 SQL 查询时格式化为本地时间文本，避免 Linux UTC 与 Windows 时区差异改变支付版本、完成月份和异议截止日。旧订单的时间列原为 `VARCHAR(64)`，保留其原始时区后缀。

## 结算与定时任务

状态使用 `draft → pushed → accepted → paid`。推送后锁定原单；异议截止日按推送次日起五个工作日（跳周末）计算并落库。缺失截止日可补齐，截止日次日自动置 `accepted` 并追加“逾期未提异议”留痕。登记线下发放要求账单已认可、凭证存在且账单与明细金额一致；模块不代发资金。

`photoWorker` 随服务启动，每分钟扫描一次，以北京时间执行月度草稿生成、截止日修复、逾期认可及账务告警；月初 00:30 后生成上月草稿，支持遗漏补跑，不修改已推送账单。worker 防止重叠执行，关闭服务等待在途任务结束。

推送和发放通知先写入 `svc_notification`，异步投递到本人绑定渠道。生产接收端由环境变量配置：

```text
PHOTO_NOTIFICATION_WEBHOOK_URL=https://实际通知接收端
PHOTO_NOTIFICATION_WEBHOOK_TOKEN=通过运行环境配置
```

请求含 `photo_id`、事件类型、消息正文以及稳定的 `Idempotency-Key`。接收端负责按 PH 编号投递本人并去重。未配置通道时保留待发记录，不标记送达；失败按退避重试，日志不输出 token 或连接详情。本次验证使用替身接收端，没有向真实摄影师发送消息。

## 初始化与存量清理

迁移命令默认只展示计划，不连接数据库：

```text
npm run migrate:photo-share
```

安装顺序为 `017_customer_service.sql`、`018_service_benefit.sql`、`019_photo_share.sql`。显式安装需要 `--apply --enable-at 含时区的上线时刻`，以明确初始统一比例的历史生效边界。迁移创建菜单、分配初始授权并初始化默认 20/20/20/8% 规则；已有版本不被覆盖，不创建登录凭据。

按 PH-Q06/07 结论取消历史回填，旧 `--backfill` 在连接数据库之前拒绝执行。存量摄影师分成、对账单、历史冲抵余额及旧摄影师财务记录使用 `npm run cleanup:photo-share` 单独盘点、生成仓库外快照并核对后清理，具体范围和恢复方式见[摄影师分成存量清理](摄影师分成存量清理-20261111.md)。账号、档案、规则、订单履约与其他主体财务保留。

清理事务追加 `finance_reset` 截止标记。支付时间不晚于切换时间的旧订单，在完成、转派或事件重试后均不再生成已清除金额；切换后的新支付正常计酬。实际只读预检发现当前连接库缺少相关分成表，结果 `ready:false`，未执行真实删除。安装、快照核对与执行清理属于上线操作。

## 回传结论落实

七项回传结论均已采用：金额样本按原实现方案验证；账单编号采用月份加 PH 编号；本期不做六个月自动到期；异议走线下；管理员建档自动创建并绑定 PH 登录账号，旧账号不处理；历史分成和既有冲抵余额走一次性清理，不再回填。确认原文与开发落实见更新后的 Excel。

当前按 `ST-P-YYYYMM-PHYYYY0001` 保证同月多人编号唯一；个人比例保留支付时点版本并可手工改回统一，按回传结论本期不做六个月自动降比例；摄影师端只读，异议由运营线下核实。若需要系统登记尚未处理的异议，应补充专用流程，避免自动认可前无法获知线下争议。逾期认可说明写入 `photo_profile_log` 的 `settle_accept` 动作；定稿日志枚举未列此动作，现不增加新字段或表，随实现文档同步记录此日志动作。

`A → B → A` 若 A 原明细已进入已推送/已发放账单，共用 `(biz_no,beneficiary_type,party_id)` 唯一约束不允许再加第二条 A 明细。当前明确返回 4311，保留已发布账本，待运营确定补发、撤销冲抵和回转方案；未发布的普通循环转派已验证。

DEMO 八行使用统一比例计算恰为 **1,734.52 元**；若把阿坤三笔改为其个人 22%，合计为 **1,838.46 元**。因此验收分别验证八行统一快照总额和 `2999 × 22% = 659.78` 的个人算法，不把两组不一致快照混为同一黄金样本。

已明确按定稿处理：完成即计不加等待天数、账单采用 pushed/accepted 状态、0.1% 步长与整数向下取整、支付时点版本、摄影师本人数据隔离、后台十列导出、在途清零后才可终止。定稿个别“本人拍完允许终止”文案解释为先完成再终止，不提供带在途强制终止。
