# 周边商品交易开发与部署

实现依据：工作区《周边商品购买与双类型订单需求设计》V1.6 及会话确认的简化发货、统一收货、客服直接发货规则。

## 已接入的代码能力

- 小程序周边规格/数量选择、购物车、地址簿、单件直购及多商品一笔全款支付；服务与实物分别展示订单及状态。
- 实物订单使用专用交易事实，原服务定金/尾款、认领、客户绑定和提成流程保持独立。
- 客服工作台新增“实物订单”。有权限的客服直接选择快递公司、填写物流单号并确认发货；提交成功自动记录处理人、锁定出库、保存包裹和物流任务，再将实物交给承运商。
- 实物按商品行及数量申请退款/退货，核实出库、退货及真实渠道退款结果；售后凭证通过原文件服务校验本人和订单归属。
- 快递100订阅、通知验签、版本隔离、轨迹保存及限频查询；退货运单单独跟踪。微信适用账号通过官方确认收货入口和服务端核对完成，不以客户端返回或物流签收冒充收货。
- 专用库存预占、确认扣减、取消安全关支付和释放、库存调整与变更保护；商品管理读取交易库存投影。

## 开发默认值

在未收到经营参数选择的情况下，按需求稿推荐值开发，全部可以由授权后台配置：

| 项目 | 默认值 |
| --- | --- |
| 购买总开关、可售商品 | 总开关关闭；没有历史商品自动开放购买 |
| 可售范围 | 运营明确启用的现货；需要照片制作的定制商品继续咨询 |
| 运费 | 所选商品的最高基础运费收一次；0 表示该商品包邮，缺少参数不能结算 |
| 配送 | 大陆快递地址；可配置允许省份；一个订单一个有效包裹 |
| 待付款时限 | 30 分钟；取消/超时须先核实并安全关闭支付意图，结果未明保留预占 |
| 数量限制 | 购物车最多 50 行、每 SKU 数量默认不超过 99、同用户最多 5 笔待付款单 |
| 售后/退货参数 | 完成后在线售后申请默认 7 天；退货期限默认 7 天，具体退费/运费由财务审核，不自动冒充渠道退款 |
| 经营联动 | 不自动计服务提成、不绑定客户、不续保护期；发货人仅记录工作处理事实 |
| 微信收货核实 | 适用微信发货管理的账号配置 `wechatReceiptRequired`，前端拉起官方入口并由服务端核实；平台结果无法验证时保持待核对 |

发布前运营需核定这些数值及售后说明。接口密钥不在业务页面维护或返回。

## 数据迁移与部署

新增独立 `lxm_physical_*` 窄表，包含地址、购物车、订单、库存、支付、售后、退款、包裹、任务及审计；成交和地址等不可变内容保存在相应实体快照。没有向已有订单宽表继续添加大批字段，也没有自动将历史服务订单转换成实物订单。

先只读审查生成的 SQL：

```bash
npm run migrate:physical-commerce
```

维护窗口完成可恢复备份、核对目标库后，部署人员显式执行：

```bash
npm run migrate:physical-commerce -- --apply --backup-confirmed
```

默认命令不载入本机数据库配置、不连接数据库；`--apply` 才读取部署环境并建表。运行时不自动 DDL。本次开发未执行上述实际建表动作、未连接真实业务库、未清空历史数据。

部署前后端需作为同一版本发布。按 [配置模板](physical-commerce.env.example) 设置快递100账号和可达回调，参考 [物流接入说明](快递100与微信实物物流接入-20261115.md) 配置微信适用账号、公司编码映射及核实流程。复用现有微信支付凭据，实物使用 `phase=full`、`PG` 支付单及 `PR` 退款单单独分流。

后台工作台的“销售配置”用于开关、可售商品、省份、支付时限、售后参数及交易库存专用调整。新版本先以关闭销售状态完成配置及联调，再逐项启用现货；配置缺失不得以演示订单或伪造轨迹替代。

### 商品新增、编辑必填信息

商品管理（影像周边）的正常新增、编辑保存（含未上架商品）均需填写商品名称、销售单位、规格模式、售价、库存、运费、商品素材和商品说明。单规格可不填规格说明，使用默认规格；多规格逐行填写规格名称、售价、库存。素材至少包含一份首图、照片或视频。编码、分类、标签、交付周期及关联打卡点保持选填。

售价必须大于 0，金额最多两位小数且不超过 10000000 元；运费可明确填 0 表示包邮，库存可明确填 0 表示售罄。新建商品的售价、库存、运费初始留空；历史缺失运费不会被自动视为包邮。前后端均校验，已上架商品再次编辑也不能清空必填信息。只下架或改为仅后台显示的历史不完整商品仍可操作，不会补造库存或运费；同时改动商品资料时需补齐信息。

填写完整后，小程序可下单还需购买总开关开启、商品被销售配置启用、商品及关联打卡点可见、非照片定制商品，且至少一个规格的可用库存（库存减去预占量）大于 0。交易库存已初始化的商品使用销售配置中的专用库存调整。

启用独立销售前需核对实物可用量，扣除历史服务订单尚未交付的周边预留量，再通过专用库存调整确认本期可售数量。已进入独立实物销售或已有实物交易库存占用的商品，暂停旧服务预约中的新加购入口，改从购物车独立购买；历史服务订单及其付款、承诺交付不自动改写。

回滚应先关闭新销售入口，保留新交易表和待处理支付/退款/物流任务，核对在途订单后再决定应用回退版本；不能删除事实表、释放尚未核实支付的库存，或退回不识别实物回调的旧支付处理程序。

## 验证与实际边界

后台运行 `npm run check`、`npm run build`、`npm test`；新增实物领域、支付分流、HTTP 身份隔离、文件凭证校验、物流适配/回调、工作台表单及模板编译测试。小程序使用 `node --test tools/test-*.cjs`，并对新增/修改页面使用微信开发者工具的 WXML/WXSS 编译器验证。

2026-11-15 开发验证记录：后台语法和结构检查通过；全量回归 1,312 项通过、19 项跳过、0 项失败。随后新增旧预约加购保护并完成 50 项交易/预约针对性回归，全部通过（实物领域目前 24 项）。小程序全量 188 项通过；新增/修改的 8 份 WXML 和 8 份 WXSS 使用官方编译器验证通过。后台实物工作台与原服务分支均通过 Vue 模板编译测试，未将此结果冒充真实设备视觉验收。

隔离测试不进行真实扣款、退款、发货或订阅。上线前仍需真实账号的微信预支付/回调/退款、快递100 HTTPS 回调与轨迹、微信发货/收货及数据库迁移往返验证。本次没有部署、上传小程序或购买外部套餐。

当前交易存储用一个 MySQL 互斥行和事务保证跨 SKU、购物车及订单一致性，适合初期单平台业务；读取会装载实物实体集合。业务量扩大时需进一步按用户/订单/SKU 分区加锁和 SQL 分页优化，不能把内存隔离测试视为生产吞吐证明。
