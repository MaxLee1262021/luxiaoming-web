# 商家扫码订单来源修复

商家分成模块生成的 `S...` 码原先只上报扫码统计，小程序没有把该入口传入订单来源，服务端下单也只支持旧版 `c=...` 码。因此扫码进入后创建的旅拍订单会显示“小程序自然来”。

## 修复行为

- 小程序立即保存本次商家码原始 scene；提交预约时使用实时来源。新扫码替换旧商家、二维码及分销员字段，旧码解析的慢回包不能覆盖新入口。
- 服务端优先校验新 scene 的校验位、已签发码、启用状态及商家状态。订单的商家、码 ID、渠道和名称从服务端数据冻结，客户端残留或伪造的商家名称、商家 ID 和旧码不能覆盖新 scene。
- 商家订单显示具体商家名称；商家列表暂时缺少该商家时使用订单保存的名称。无商家参数的直接冷启动清除历史商家入口，订单继续显示“小程序自然来”；预约内部跳转、支付或授权返回前台保留本次来源。
- 来源解析不依赖扫码统计请求先完成，也不依赖 `SHARE_ENABLE_AT`。解析不会新增扫码、绑定或分成记录，财务分成规则仍由现有流程判定。
- 旧版商家码继续支持，同码内部跳转保留已解析的城市和铺放位置。待支付预约的来源在提交时冻结，支付成功转为正式订单时继承该来源。

## 发布与验收

后台更新本次源码并重启服务，同时将 `luxiaoming_交付包/miniprogram` 上传为新的体验版或正式版。无需新增数据库结构或执行迁移。应先更新服务端，使其具备解析新 scene 的能力，再切换小程序版本。

使用商家 A 的有效码进入并完成预约，后台订单来源应显示 A；扫码 B 后再次预约应显示 B。直接冷启动进入小程序下单应显示“小程序自然来”。同时检查待支付预约支付后来源保持一致，停用码不能被默默当成自然来源或旧商家来源。

本次未修改已有订单。缺失商家来源的历史订单须结合下单时的可核验扫码记录单独核对，不能按用户最近一次扫码批量回填。
