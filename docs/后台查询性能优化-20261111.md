# 后台查询性能优化

本次按主要后台查询低于一秒的目标，对内容商品、订单模块、系统日志、权限、商家分成、客服分成和摄影师分成做了实际测量和优化。当前版本不需要新增数据库迁移，不重算历史财务数据。

## 处理内容

- 结构检查批量读取 `information_schema`，冷健康检查保留缺列、索引、孤立属性和财务扩展字段检查，避免每张表单独查询。
- 通用集合支持 `listMany(keys)`，同一请求合并属性查询，空集合不查询关系表；记录和集合间保持隔离，字段和关系顺序不变。
- 模块查询共用本次请求的列表和配置文档结果，内容可见性计算复用读取结果。不会在不同请求间缓存业务数据或授权结果。
- 权限人员、角色菜单、能力授权批量读取，登录及会话刷新在一次请求内复用新鲜的策略结果，账号停用和菜单撤销仍实时检查。
- 客服和摄影师查询按接口读取依赖，查询不加载手机号唯一性检查、通知队列、无关财务或审计历史；写入事务及财务锁定校验保留。
- 摄影师列表在途订单统一批量读取，避免每位摄影师两次查询。商家配置、分页明细、二维码和统计减少逐行关联查询。
- MySQL 连接默认启用协议压缩，减少远程数据库大量结果的传输时间。服务端不支持压缩时由协议协商关闭，可设置 `DB_COMPRESS=false` 显式禁用。
- 大于 16KB 的成功 GET JSON 在客户端允许时使用 gzip，不改变响应内容、权限过滤或缓存规则。小响应、写操作和错误响应保持原有发送方式。

## 当前环境实测

在本机 API 处理器连接当前远程 MySQL 的环境中，只读测量 61 个有效查询入口、300 次成功请求，全部低于 1,000ms，整体 P95 为 412ms，最大 939ms。39 个主入口各测六次，其余补充入口各三次。不存在的探测路径返回 404，不计为有效接口。

| 接口 | 优化前单次 | 优化后 P50 | 优化后 P95 |
|---|---:|---:|---:|
| 健康检查 | 5229ms | 15ms | 295ms |
| 系统日志及回收站模块 | 1981ms | 421ms | 458ms |
| 权限人员列表 | 863ms | 167ms | 207ms |
| 摄影师列表 | 1212ms | 281ms | 303ms |
| 客服人员列表 | 1336ms | 254ms | 284ms |
| 商家分成配置列表 | 834ms | 393ms | 463ms |

对照表的优化前为一轮采样，优化后为多轮分位数，网络本身存在波动。当前订单和分成账本数据较少；内容商品、1,803 条审计日志和 61 条回收站数据均为当前真实数据。本轮不是生产高并发或大订单量压测，不保证任意网络、任意负载均低于一秒。进程首次建立 DNS、TCP 和 Redis 连接可能增加冷启动耗时。

每个入口的 P50、P95、最大值和 SQL 次数见工作区 `outputs/admin-query-performance/后台查询接口优化报告-20261111.md`；原始数据为同目录 JSON 文件，不包含凭据、令牌或客户正文。
