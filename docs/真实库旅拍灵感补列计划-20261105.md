审批后的执行顺序：

1. 确认已有可恢复备份；在数据库客户端选择真实服务配置的同一个库，核对脚本首条 `SELECT DATABASE()` 的结果。
2. 在单个会话运行该独立 SQL。两条 `ALTER TABLE` 可能取得元数据锁或重建表，选择合适维护时段；MySQL 5.7 DDL 会隐式提交，不能承诺事务回滚。
3. 核对最后的只读查询：两行类型分别为 `varchar(255)`、`text`，`IS_NULLABLE=YES`，默认值为 `NULL`。
4. 再检查 `http://127.0.0.1:5192/api/health`，以列级健康结果为准；若仍使用短时健康缓存，缓存过期后重查。检查后台真实数据加载与灵感读取，不新建测试业务记录。

此操作不修改已有业务字段值，不回填历史富文本，不处理扩展属性。若回退应用版本，可保留这两个兼容的可空列；本计划不包含删列回滚。

不要用完整的 `npm run migrate:mysql -- --apply` 代替这个补丁。完整迁移默认不导入本地 JSON、没有演示 seed，但仍会建表/补列、调整索引和授权结构、转换历史载荷、更新 schema version、归一化配置/生命周期以及清理属性，范围明显大于这两列。`--dry-run` 仅给出本地迁移计划，不连接目标库验证缺列。`scripts/check-mysql-readonly.cjs` 已验证连接、业务表与列合同；索引及历史数据一致性的完整就绪状态仍以 `/api/health` 为准。
